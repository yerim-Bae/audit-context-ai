# ADR 0006 — 첫 화면은 Next.js 대신 정적 렌더링으로 만든다

- 날짜: 2026-08-05
- 상태: 승인됨 (기술적 판단, ADR 0001의 연장)

## 맥락

`CLAUDE.md`는 웹 화면을 Next.js App Router로 만들도록 규정합니다. 그러나 첫 세로 흐름은 다음 조건을 모두 만족합니다.

- 데이터가 읽기 전용이고 시드에서만 옵니다(ADR 0001)
- 로그인, 서버 상태, 폼 제출, 실시간 갱신이 없습니다
- 사용자는 개발자가 아니며, 합격 기준이 "README 안내만 따라 로컬 화면이 열리는가"입니다

Next.js를 도입하면 런타임 의존성 수백 개와 빌드 파이프라인이 들어오는데, 첫 화면이 하는 일은 미리 만든 25개 Claim을 보여주는 것뿐입니다.

## 결정

시드 데이터를 읽어 **하나의 정적 HTML 파일**을 생성합니다.

- 렌더러: `src/render/page.ts` — 순수 함수 `renderPage(seed) → string`
- 빌드: `npm run build` → `dist/index.html` + `dist/sources/`(원문 파일 복사)
- 실행: `npm start` → `node:http` 기반 초소형 정적 서버. 외부 패키지 없음
- 브라우저 JS는 **보이기/숨기기와 근거 창 열기만** 담당. 화면의 모든 문장은 HTML에 미리 들어 있음

런타임 의존성은 0개입니다. 개발 의존성은 `typescript`, `prettier`, `@types/node` 세 개뿐입니다.

## 이 선택이 만들어 낸 이점

화면에 나오는 모든 내용이 생성된 HTML 문자열 안에 있으므로, **브라우저 없이도 화면 규칙을 검사할 수 있습니다.** `tests/render.test.ts`의 16건이 그렇게 동작합니다. 예를 들어 "회사 특정 Claim이 사실로 표시되지 않는다"를 마크업 수준에서 확인합니다.

## 비용과 한계

- **Playwright 같은 브라우저 e2e 테스트가 없습니다.** 단계 전환과 근거 창 열림은 실제 브라우저에서 사람이 확인해야 합니다. 화면 테스트는 마크업 검사이지 e2e가 아닙니다. 이 구분을 흐리게 보고하지 않습니다.
- PDF 원문(약 3.7MB)을 `dist/sources/`로 복사하므로 빌드 산출물이 커집니다.
- 화면이 복잡해지면(검토함의 승인·반려, 필터 상태, 업로드) 정적 렌더링의 한계가 옵니다.

## 재검토 조건

다음 중 하나가 생기면 프레임워크 도입을 다시 판단하고 새 ADR을 씁니다.

- 사용자가 화면에서 데이터를 바꾸기 시작할 때(Claim 승인·반려)
- 파일 업로드가 필요할 때
- 사례가 여러 개가 되어 라우팅이 필요할 때
