# Source and Claim Policy

이 문서는 MVP에서 출처와 주장을 다루는 최소 규칙이다. 구현 중 변경하려면 `docs/decisions`에 ADR을 남긴다.

## 1. 주장 상태

- `FACT`: 근거 원문이 주장을 직접 지지하고, 적용 범위가 일치한다.
- `INFERENCE`: 확인된 사실에서 합리적으로 도출했지만 직접 확인되지 않았다.
- `UNVERIFIED`: 필요한 근거가 없거나 충분하지 않다.
- `CONFLICTING`: 둘 이상의 근거가 서로 양립하지 않는다.

주장 상태와 사람의 검토 상태는 별도다. 검토 상태는 `AI_EXTRACTED`, `HUMAN_VERIFIED`, `REJECTED`, `STALE`을 사용한다.

## 2. 출처 등급

- `S`: 법령·기준 원문, 서명 계약, 은행조회서, 원장·시스템 원본
- `A`: 감독기관·표준제정기관·산업기구 공식 문서, 감사받은 공시
- `B`: 회사 공식 홈페이지·IR·정책, 공식 서비스 제공자 자료
- `C`: 신뢰도 높은 전문 매체·학술·전문가 자료
- `D`: 블로그·커뮤니티·검색 요약·출처 불명 자료

D등급 출처는 탐색 키워드 생성에만 사용하며 FACT의 단독 근거가 될 수 없다.

## 3. 범위 규칙

- 범위는 `INDUSTRY`, `COMPANY`, `PERIOD`, `TRANSACTION`으로 명시한다.
- 산업 일반 자료는 특정 회사가 해당 거래나 담보를 실제로 사용한다는 사실을 증명하지 못한다.
- 특정 회사의 정산주기, 담보, 질권자, 금액은 회사 계약·조회서·명세 등 회사 특정 자료로 확인한다.
- 근거 범위보다 넓은 주장은 FACT가 될 수 없다.

## 4. Evidence 최소 요건

FACT는 최소 한 개의 직접 지지 Evidence Span을 가져야 한다. Evidence Span에는 다음을 보존한다.

- 원문 스냅샷과 해시
- 출처 제목, 발행자, 버전, 수집일
- 페이지·절·문단·좌표 또는 재현 가능한 locator
- 주장을 직접 지지하는 짧은 원문 발췌
- 지지·반박·맥락 중 관계

링크만 저장해서는 안 된다. 출처가 바뀌면 기존 Claim을 삭제하지 않고 `STALE` 검토 대상으로 표시한다.

## 5. 숫자와 날짜

- 숫자와 날짜는 원문과 정확히 일치해야 한다.
- 계산값은 원문 입력값과 산식을 함께 저장한다.
- 모델이 숫자나 계약조건을 보충해서는 안 된다.
- 확인되지 않은 숫자는 빈칸으로 숨기지 않고 UNVERIFIED로 표시한다.

## 6. 감사 연결 표현

- 시스템은 유의적 위험, 회계처리 적정성, 감사절차 또는 감사의견을 확정하지 않는다.
- 위험은 “가능성이 있어 추가 확인이 필요함”으로 표현한다.
- 요청자료와 인터뷰 질문은 어떤 Claim과 거래 단계에서 나온 것인지 추적 가능해야 한다.
- 미확인 항목은 요청자료 또는 인터뷰 질문으로 전환한다.

## 7. MVP 출처 사용

- BSP 산업 일반 사실은 IATA 공식 자료를 우선 사용한다.
- 회계기준 관련 사실은 공식 기준서 또는 표준제정기관 자료를 우선 사용한다.
- 가상 여행사 사례에는 산업 일반 FACT와 명시적으로 가정한 데모 데이터를 분리한다.
- 실제 회사명은 회사 특정 근거가 확보되기 전에는 사용하지 않는다.
- 가상 회사의 계약서·조회서 등 데모 문서를 만들지 않는다. 따라서 `COMPANY` 범위 Claim은 `FACT`가 될 수 없다([ADR 0004](decisions/0004-no-fabricated-company-documents.md)).

## 8. 구현 가능한 규칙과 검사

위 규칙 중 자동으로 검사할 수 있는 것을 기계가 판정 가능한 문장으로 다시 적고, 실제 검사와 연결합니다. 검사는 `npm test`로 실행합니다.

| # | 규칙 (판정 가능한 형태) | 검사 |
|---|---|---|
| P1 | 상태·범위·등급·근거관계 값은 정의된 열거값에만 속한다 | T2 |
| P2 | `FACT` Claim은 `relation = SUPPORTS`인 Evidence Span을 1개 이상 갖는다 | T3 |
| P3 | 모든 Evidence 참조는 존재하는 Span과 존재하는 Source로 이어진다 | T4 |
| P4 | `FACT` Claim의 지지 출처는 `can_support_scope`에 그 Claim의 `scope`를 포함한다 | T5 |
| P5 | `scope = COMPANY`이면서 `assertion_status = FACT`인 Claim은 0건이다 | T6 |
| P6 | `snapshot.sha256`과 `snapshot.bytes`가 없는 출처, 등급 `D`인 출처는 `FACT`를 지지할 수 없다 | T7 |
| P7 | 등록된 모든 스냅샷 파일이 실제로 존재하고 저장된 해시·크기와 일치한다 | T8 |
| P8 | 모든 인용문은 지정한 페이지의 원문 텍스트에 실제로 존재한다 | T9 |
| P9 | `INFERENCE`는 전제 Claim 1개 이상과 추론 설명을 가지며, 직접 근거를 갖지 않는다 | T10 |
| P10 | `UNVERIFIED`는 요청자료 또는 인터뷰 질문 1개 이상으로 전환되고, 그 대상이 실제로 존재한다 | T11 |
| P11 | 위험 문구는 "가능성"과 "확인"을 포함하고 확정 표현을 포함하지 않는다 | T14 |
| P12 | 모든 요청자료·인터뷰 질문은 위험과 Claim으로 역추적되고, 모든 위험은 최소 하나의 확인 행동으로 이어진다 | T15, T16 |

### 인용문 대조 방식

인용문이 원문에 있는지 확인할 때 양쪽에 같은 정규화를 적용합니다(`src/domain/rules.ts`의 `normalizeForQuoteMatch`).

1. 모든 공백 제거 — PDF 추출이 낱말 중간에 공백을 넣는 문제를 흡수
2. 둥근따옴표·아포스트로피를 곧은 문자로 통일
3. 각종 대시를 하이픈으로 통일
4. 글머리표(`•` 등) 제거

단어·어순·숫자는 바꾸지 않습니다. 따라서 요약하거나 바꿔 쓴 인용문은 검사에서 실패합니다.

### 아직 자동 검사하지 못하는 것

- "중요한 주장인가"의 판정 기준이 없어, 중요도에 따른 검사는 불가능합니다. 현재는 **화면에 표시되는 모든 단정형 문장이 Claim이어야 한다**는 규칙으로 대체할 계획이며, 화면이 만들어지는 4단계에서 검사합니다.
- 인용문이 해당 주장을 **의미상** 지지하는지(citation precision)는 사람이 판단합니다. 현재 20건은 모두 사람이 원문과 대조했습니다.
- 출처 원문이 나중에 바뀌었는지는 자동으로 감지하지 못합니다. 재수집 시 해시 비교로 확인합니다.
